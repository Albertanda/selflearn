# 执行与审查流程 2.1：按阶段交接与探索包复用

生效日期：2026-10-11；由用户明确要求替换逐卡人工交接。业务目标和C01–C13保持，小卡仍是编码/测试单元，授权、会话、汇报、独立审查改为阶段。此文件优先于历史单卡提示词中“完成一张卡就停止”的说明。

## 1. 两种粒度

57张小卡保留，作为明确的目标、符号范围、文件范围、必需行为测试和完成条件。每个阶段包含2–6张卡，执行者在同一个阶段会话里按顺序完成、测试、自修，阶段内不再请求下一张卡批准。阶段结束提交一份汇总，协调者一次复核；不自动进入未授权的下一阶段。

阶段顺序和范围见stages.json；tasks.json中的dispatch_order已同步为阶段内顺序的展开。S00是本次协调者修补/签收的P1-00，后续从S01开始。S13–S15为集成/环境验收，最后浏览器卡单独成阶段是验收门，不是恢复逐卡交接。

保持一名廉价执行者串行编码，一名协调者独立审查。共享文件多，不在当前项目试点多执行者并行，也不让执行者自己标accepted。协调者在已授权阶段范围内可直接修小缺陷并复测，明确列出自己改的文件和补充测试，不再为一处断言多增加一轮用户转发。

## 2. 阶段执行规则

1. 优先读取本阶段开工指令及其“已探索文件清单+关键片段”包，核对当前前置receipt及片段hash，再按本阶段卡和契约编码。已提供片段可作为定位输入；只按待实现符号、确需的上下文或hash变化定向补读，不重新阅读全部仓库和57卡，不复述整个项目，不先提交orientation报告。
2. 阶段开始记录source/data基线。阶段允许文件为卡白名单并集，但仍遵守卡的符号与业务目标，不能利用大文件的并集范围顺手改其他功能。
3. 一单元改完立即运行其定向行为测试。通过后记录本地结果，直接继续本阶段下一单元；不要每单元产一份长报告和一次source tar。
4. 阶段共用的node/tsc/lint等命令通常在末尾合并一次；有新变化或失败才追加复跑。全量pytest仍归S13，前置阶段只跑相关测试。
5. 相同阶段内的已通过单元可以为真实集成失败作必要修正，记录返修原因和关联回归；不把它标成跨范围阻塞。需要改不在阶段并集内的生产文件或改变数据契约时，才blocked_scope。
6. 250行是最初拆卡评估提醒，现改为阶段复杂度预警，不能机械截断、压缩长行或新造补卡税。预计一个阶段变成架构重写或无法独立验证，应给协调者一个最小拆分建议；范围和验收不能被行数替代。
7. 缺真实沙箱/浏览器时记录blocked_environment；不能通过skip/fake结果声称验收完成。无环境依赖的实现单元仍可在本阶段内完成并如实报告。
8. 阶段内安全/真实数据保护失败立即停；普通失败先自修。阶段末只有一次对外汇报，等待协调者复核。不提交/推送/升级、不启动真实服务、不调用真实供应商，不处理第二阶段新功能。

## 3. 最少证据文件

每阶段默认只保留三个主要文件：

```text
.phase1-evidence/stages/Sxx/report.json      阶段汇总与各单元结果
.phase1-evidence/stages/Sxx/execution.log    命令、时间、原始输出、实际exit code；仅追加
.phase1-evidence/stages/Sxx/review.json      协调者审查、补修、当前源码hash和签收
```

另加必要的source/data基线和一个阶段完成source归档；不为每条断言、每次检查、每卡反复建目录。先前P1-00的原始证据保持不变，新的协调者修补在reviews/P1-00，不覆盖原completion或失败日志。

report.json内card_results记录卡ID、verified_local/blocked、目标是否达成、修改文件、满足的完成条件、测试名和日志定位；直接复用命令记录，不强制每卡completion.json。历史Completion schema和单卡证据仍可读；新阶段使用StageReport schema。

日志是原命令输出，不是事后写一行“pytest→0”。去掉真实密钥，不删除失败尝试；返修只追加修订记录和复测。大二进制只存一次，其hash列入report，不把同一snapshot复制成多份证明。协调用review.json完成签收，不再同时写开工说明/补修说明/最终验收四份重复文件。

## 4. 反馈必须成为可执行检查

| 已重复出现的缺陷 | 执行者必须做的检查 | 协调者复核 |
|---|---|---|
| 错误响应回显输入/秘密 | 32KiB合法输入或异常cause中放唯一虚构标记；响应不得含标记，消息有长度界限；不能只截断到512字符 | 检查HTTP/WS/tool完整序列化结果 |
| 非法输入负例本身不完整 | 先证明base合法，再只修改一个目标字段/故障点；明确期待在哪层拒绝 | 检查其余字段合法，避免因另一错误而“通过负例” |
| bool与int内容相等掩盖错误 | 真正布尔、整数的边界测试，如size=True不能当1，correct="false"不能当False | 查看类型约束及独立反例 |
| regex全字符串校验接受换行 | 长度边界、末尾LF/CRLF/空格反例；JSON Schema采用真实字符串结束约束，Python用fullmatch | schema和实现两层都验证，不只局部绕过 |
| 测试观测不到缺陷 | 高风险行为做一个针对性坏对照：把关键效果改掉/移除，应使对应断言失败 | 协调者在临时副本/monkeypatch中独立复核；不要求每个琐碎修改做4份mutation报告 |
| 事务失败却改学情/留下产物 | 在提交点前后注入故障，对磁盘bytes、发布URL、残留文件作断言 | 不以“mock没调用”或“退出0”代替状态证明 |
| 假安全/串科 | 同名A/B/global、别run/别用户、越界路径等独立fixture | 系统沙箱与应用策略分开，真实环境门不可替代 |

这些检查是相应风险单元的最低证据，不是每张无关文档卡都增加全部检查。错一个共同基础就及时修基础和受影响消费者，不因最初“冻结”而拖到后面几十卡。

## 5. 协调者阶段审查

读统一diff、report和日志，核对实际路径和命令；独立重跑关键正/反例和高风险边界。低风险阶段只定向复核；存储、授权、报告执行与发布、导出需要更强的独立探针，阶段S13才全量回归。

遇少量实现/断言问题，协调者在用户已授权范围直接修并追加记录；如问题较多，用一个按单元ID列的返修清单，执行者同阶段返修一次后整体复核。更改共享契约必须记录契约版本和受影响单元，不能改断言迎合错误实现。

阶段签收状态来自实际代码和测试，不来自passed计数或Schema字段齐全。高驳回率、文件数量、代码/测试行数比不是成功或成本的单独证明；记录实际返修次数、阻塞原因和运行命令次数即可，不让执行者手工编造费用统计。

## 6. 快照工具修补后的使用约定

scripts/phase1_snapshot.py已修为v2：mode保留、严格输出路径、归档hash先检查、安全解包、不修改原baseline、流式打包校验、精确范围/glob、完整保护根清单。

- capture默认包含P1-00自身新代码；用--include为已验收和当前阶段明确批准的新源码追加精确路径/glob。未知未跟踪源码仍不归档，但范围检查会发现。
- archive不再回写baseline，生成单独的`.tar.gz.manifest.json`；verify-rebuild自动读sidecar，也能读取历史带archive_sha256的baseline。原始baseline/旧tar不要重新生成或覆盖。
- 每阶段起止source/data基线与scope compare即可；完成时一个恢复归档。允许测试缓存web/dist/node-tests，其余未知源码改动不能用缓存名掩盖。
- 对旧v1保护记录只能确认它曾记录的byte/link，无法补造当时未记录的mode和被排除条目。新v2起止检查包括隐藏文件及权限，作为后续阶段的正式基线。

当前入口以stages.json的next_stage和最新签收receipt为准；历史START_Sxx不表示今日授权。

## 7. 派发时附探索包（2026-10-13新增）

协调者每次授权新阶段，随START_Sxx给一份探索包：已查看的确切路径/符号或行段、SHA256、与各卡的关联、原样关键片段、已知故障与前置接口、尚不存在的新文件。注明探索日期和对应receipt；不要把局部探索写成“全仓库已探索”。例如S04使用S04_EXPLORATION.md。

worker先核hash和前置签收，复用片段直接编码。hash未变时无需为orientation重读这些文件；定位/实现确需补读时仅读有关段落。hash变化则读取差异和最小上下文，不能覆盖文件恢复旧hash，也不能把读取缓存当成免验证代码的理由。测试、坏对照、起止数据/范围与归档证据要求保持；探索包不增加每卡汇报税。阶段结束后由协调者为下一阶段刷新包，worker不自行跨阶段探索或实施。
